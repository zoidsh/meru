# CLAUDE.md

Meru is an Electron client for Gmail and Google apps. The design, principles, glossary and decisions live outside this repository, in `$PROJECT_DOCS_DIR/zoidsh/meru/next` (`~/projects/docs/zoidsh/meru/next` on the maintainer's Mac); read `principles.md` and `architecture/design.md` before changing structure, and use the glossary's words.

The app is `app/`, a workspace package whose `package.json` holds its name, version, description, `main`, runtime dependencies and Electron; it builds into `app/dist/`. `packages/` holds the leaf packages that serve it and import nothing from it, which lint enforces, `packaging/` electron-builder, `tests/` the end-to-end suite and `scripts/` the development scripts. The root `package.json` holds only the workspace, the scripts and the toolchain.

## Commands

`mise install`, then `pnpm install --frozen-lockfile`. mise puts `node_modules/.bin` on PATH, so `vp` and `tsc` run bare.

| Task | Command |
| --- | --- |
| Run the app, rebuilding on change | `pnpm dev`, with `--profile <name>`, `--background`, or any Electron argument |
| Lint, format check, format | `vp lint`, `vp fmt --check`, `vp fmt` |
| Typecheck | `tsc --build` |
| Unit tests | `vp test run`, one file `vp test run <path>` |
| Everything before a push | `pnpm check` (format, lint, types, tests) |
| Build into `app/dist/` | `pnpm build` |
| End-to-end, against `app/dist/` | `pnpm test:e2e`; on Linux `xvfb-run -a -s "-screen 0 1920x1080x24 -noreset" pnpm test:e2e` |
| Package an unpacked app into `packaging/out/` | `pnpm package` |
| Package installers, signed when the env is set | `pnpm package:mac`, `package:linux`, `package:win` |
| Signed installers from CI, as run artifacts | `gh workflow run build.yml --ref next` |
| Measure CPU and memory, against `app/dist/`, macOS only | `pnpm measure`, `pnpm test:budget` |

## Layers

> `core` imports nothing of ours and nothing of Electron's. Features import `core` and each other's types. `platform` is the only layer with a value import from `electron`.

> No module constructs a singleton at import. `index.ts` in main and the page entry in the renderer build the object graph.

> Adding a feature is additive: its diff touches its own directory, one line in `index.ts`, the glossary and the changelog.

`oxlint.config.ts` enforces the layers under `app/` with `no-restricted-imports` per directory, plus `import/no-cycle`; `es-toolkit`, like zod, is a runtime dependency every layer may import, `clamp` and `isEqual` among it, while `execa` is for `scripts/` and refused under `app/`; `core/values.ts` holds what es-toolkit lacks, `parseField`, `messageOf` and `stepFrom`. A preload value-imports `electron` only in its `bridge.ts`. The renderer and preloads never import `main`, with one exception: a feature's `settings.ts` and `commands.ts` are its half of the contract every page reads, so they compile with `shared`, the registries in `shared/*/registry.ts` import them, and lint holds them to what `shared` may import.

## Tests

> No test replaces one of our own modules. Doubles exist only at ports, one hand-written fake per port in `app/test/fakes/`, an object literal that `satisfies` it or a small class that `implements` it, never a cast.

No `vi.mock` anywhere. A feature's test assembles it as `index.ts` does, over the shell's real `IpcDispatcher` and `CommandDispatcher` with a `FakeIpcTransport`, which lint lets a feature's test import from `main/shell/`. Unit tests sit beside their file as `*.test.ts`; Vitest runs `core`, `shared`, `main`, `packages/user-data`, `packaging` and `scripts` in Node and `preload` and `renderer` under happy-dom. Core's tests compile in `core/tsconfig.test.json`, which may take the fakes, since the fakes import core. Helpers every test may share sit in `app/test/`, a project of its own: `result.ts`'s `unwrap`, which throws a failed `Result`'s error, and `random.ts`'s seeded `random(seed)`, which the property tests and the profiles' random run draw from. `scripts/check-layers.test.ts` imports every `core/` and `main/features/` module with nothing faked. A renderer component's test renders it with `renderer/testing.tsx`'s `mountChrome` or `mountSettings`, under the stores its page mounts, `renderer/page.tsx`'s `chromeStores` or `settingsStores` (the chrome page's with the launcher's provider too), over one `FakeBridge`, which answers each request with the `answer(channel, value)`s it is given, a value checked against the channel's result schema; `push(channel, payload)` and `sentOn(channel)` take channel objects too, the mount unmounts itself when the test finishes, and `typeInto(field, text)` and `settle()` type into a field and let pending answers arrive. End-to-end tests are `tests/*.e2e.ts`; `scripts/lib/app.ts` launches the app, finds a page by a part of its URL through `pageOf(app, part)`, sends a request as the chrome page would through `invokeIn(page, channel, payload)` and reads what main exposes for a test through `readExposed(app, key)`, for the suite and `pnpm measure` alike. `tests/app.ts` holds the suite's `test`, whose fixtures, `launch`, `userData`, `stub` (the entitlement API's) and `feed` (Gmail's feed's), tear down whatever they started however a test ends, so a test writes no `try`/`finally`, and the suite's readers, such as `inspect`, `stageOf` and `must`, which fails on a missing value rather than letting an assertion run on a stand-in; `tests/` imports `scripts/lib`, never the reverse.

## Comments

A comment says only what the code cannot: an outside constraint, such as Electron, Chromium, Gmail, a platform or a tool, or why the obvious approach was rejected. Never what the code does, and never a reference to a principle.

## Commits

One commit per logical change. The subject says what changed in at most 72 characters; after a blank line, a body of a few sentences says why: the constraint, the approach rejected, what moved. A port from 3.x takes its behaviour, never the shape of its code: read 3.x for what it does and for what it does badly, such as tangled responsibilities, hidden state, unbounded retries, untested DOM pokes or comments that lie, and let the port fix each.

## Stage

`main/features/stage/` owns one `Stage` per window: the view of each pane of the group the window shows, and overlays such as the drag overlay. The group, its layout and its tabs belong to the profiles feature: the stage reads them on every `stage.invalidated` event, a split adds the tab of the app the launcher picks into the group beside the focused pane, through `stage.openTab`, closing a pane closes its tab, and a drag writes its ratio once, on release. The stage's reconcile is the only code that calls `addChildView` or `removeChildView`: it applies the operations the pure `core/engines/stack.ts` plans, `stackOf` putting panes in layout order with overlays above them and `stackPlan` reordering by removing and inserting, because Electron moves an attached view to the top whatever index it is given. Geometry comes from the pure `core/engines/layout.ts`, as does which pane shows a tab and which tab a pane shows (`paneOfTab`, `tabOfPane`), a pane's drop zones (`dropZoneAt(rect, point)`, the outer fifth by each edge for that edge and the middle for a join after it, `placementOf(zone)` and `dropRect(rect, zone)`, the half or the whole the tab would take, and `dropTargetAt(panes, point, tabId)`, the pane under the point with the zone and the rect, nothing over the tab's own pane, a pinned pane's left and top fifths landing on its right and bottom so the pinned tab stays first, which the snapshot's `pinned` on each pane tells it, which the stage's drop and the drag page both read), and what of the group's layout the stage shows, `shownLayout(layout, { drag, maximised, fullscreen })`: a divider drag's layout while one is on, and of it only the fullscreen tab's pane, else only the maximised tab's. The panes fill what the chrome leaves of the content area, `core/engines/chrome.ts`'s `stageArea` of the content area and the `insets` the stage reads on every layout, `chromeInsets(sidebar)`, the titlebar's `TITLEBAR_HEIGHT` on top and the sidebar's width on the left, which gives the area and the sides where the panes keep no inset (`flush`); `Stages.relayout()` lays every stage out again on the `sidebar.changed` event the sidebar feature emits. Anything drawn over a pane is a view the stage stacks above them: the drag overlay (`drag-overlay.ts`'s `DragOverlay`, which holds a drag from `beginDivider(splitId)` or `beginTab(tabId, url)` to `end`: a divider's, reading the group's layout and handing it the ratio on release, or a sidebar row's, `{ kind: "tab", tabId }`, whose view is the overlay page of kind `tabDrag` on `tabDragSurface`, at the address `main/index.ts`'s `tabDragUrl(tab)` gives, carrying the tab's `appId`, its `title` and its profile's colour as `accent`, each left out when the tab has none, and refused with `unknownTab` for a tab the profiles do not know, which main sends the pointer the chrome page reports as the `drag.pointer` push; on a row's release the stage joins the tab beside the pane under the point, on the side of its drop zone (`placementOf`), keeping focus on the tab that had it, and a release off every pane or over the tab's own pane changes nothing; Escape cancels either drag through `stage.cancelDrag`, sent by whichever page has the keyboard, the chrome page's dividers or the drag's own page, which a tab drag focuses once it has loaded, since Electron leaves the keyboard with the page the row was pressed in, and which hands it back to the focused pane when the drag ends, and a cancel from the drag's page reaches the chrome page as the `stage.dragCancelled` push, on which the sidebar ends its dnd-kit drag), and an overlay (`overlay.ts`), which `openOverlay(kind, url)` shows as a transparent view over the whole window holding a renderer page on the surface of its kind, such as the launcher's, focused once it has loaded, and `closeOverlay()` takes down, giving focus back to the focused pane. Both report alike, through the `onOverlay(contentsId, surface | null)` and `retire(owned)` options the stage gives them: the first as a view comes, on its surface, and goes, the second handing back a view to detach before it is disposed. The stage's channels are the drag's, `stage.snapshot` and `stage.openTab`; every other action on a pane is a command, and the snapshot's `navigation` carries its history for the titlebar, and each of its `panes` the pane's `paneId`, the `tabId` it shows and its `rect`; the stages answer `stage.openTab`, which the launcher sends, bringing the profile's tab of a single-instance app to the front (`Profiles.openTab`) and otherwise adding a tab of the app, beside the focused pane in the orientation its optional `split` names, as `launcher.open` takes one; on `tab.focused` every stage focuses that tab's pane. `tab-views.ts`'s `TabViews` keeps a view per tab, made the first time the tab is shown, its spec built from the profile's partition and the address and zoom of the stage's `sourceOf(tab)`, and kept, detached, while its group is not, so a split, a join, a leave or a switch of group never reloads a page; a view goes only once its tab is closed, its profile removed or it falls asleep (`Stages.sleep(tabId)`, which lets go of it only while no pane shows it). `Stages.load(tabId, url)` loads an address into every view of the tab a stage keeps, or, while none does, keeps it as the address the tab's next view starts at, without making it the tab's stored address. `Stages.shown()` answers the tabs a pane shows and `Stages.audible()` the tabs whose page plays sound, `ViewPort.audible()`. The stage tracks focus by tab and answers it as the pane showing that tab. A page's fullscreen request reaches the stage through `ViewPort.onFullscreen(listener(entered))`, Electron's `enter-html-full-screen` and `leave-html-full-screen`; Electron takes the window fullscreen and back by itself, so the stage only gives that tab's pane the whole window, square, over the chrome, the other panes detached, through `shownLayout`'s `fullscreen` and `layout`'s fullscreen pane, and must not set the window's fullscreen as well, which left the page stuck in fullscreen; the stage forgets the fullscreen tab when its pane closes or the group shown changes. Every view is made through the stage, which attaches the shortcut keys and hands back an `OwnedView` (`owned-view.ts`, with `CANVAS`, `TRANSPARENT` and `loadOwned`) to dispose; every view's `ViewSpec` names its background: `CANVAS`, white, for a pane whatever the theme, since a page that sets no background of its own paints the view's colour and assumes a browser's white canvas, and `TRANSPARENT` for an overlay. A feature tears down what it attached through one `DisposableStore` (`core/disposable.ts`) in `dispose()`. The stage declares its commands in `commands.ts`, each in the View menu: `stage.splitVertical` (Cmd/Ctrl+Alt+N) and `stage.splitHorizontal` (Cmd/Ctrl+Alt+Shift+N), which split nothing themselves but emit `split.requested` with the window and the orientation, on which the launcher opens to pick the new pane's app, `stage.closeTab` (Cmd/Ctrl+Shift+W), which closes the focused pane's tab and so the pane, and refuses the last one, `stage.focusNext` and `stage.focusPrevious` (Cmd/Ctrl+Alt+. and ,), which move focus through the panes in layout order, `stage.reload` (Cmd/Ctrl+R), `stage.swap` (Cmd/Ctrl+Alt+S), which trades the focused pane's place with the next one's in layout order through `Profiles.swapPanes`, `stage.equalise` (Cmd/Ctrl+Alt+=), which evens every run of the group's splits through `Profiles.equaliseGroup`, `stage.maximise` (Cmd/Ctrl+Alt+M), the three pane keys one family differing only in the last key,, which gives the focused pane the whole stage and hides the others until it runs again, another pane is focused, a tab closes or the group changes, held per window by tab and never stored as the pure `core/engines/spotlight.ts`'s `Spotlight`, which also holds the fullscreen tab and decides both through `toggleMaximised`, `afterFocus`, `afterClose` and `afterFullscreen`, and `stage.stop`, with no menu item or shortcut, which the titlebar runs; `stage.back` and `stage.forward` sit in a History menu, on Cmd+[ and Cmd+] on macOS and Alt+Left and Alt+Right elsewhere, as 3.x has them. Cmd/Ctrl+W is kept for closing the window. The setting `appearance.style` picks `modern`, inset rounded panes, or `classic`, edge to edge with 1px seams, which the sidebar, the titlebar and the dividers draw as `STYLE_METRICS`'s `seams` says, and `stage.zoom` the panes' zoom per profile; a change to either lays out or zooms the panes again. `MERU_E2E=1` loads `about:blank` in panes; it and `MERU_MEASURE=1` count only in a run from the repository, never in a packaged app. No page is allowed a channel only a test needs: under it `main/shell/e2e.ts` leaves a function on `globalThis.meruE2e` answering the bounds of each child view, `panes`, each pane's `{ tabId, contentsId, zoom }` in layout order, and the menu's accelerator by command id, and under `MERU_MEASURE=1` `main/shell/measure.ts` one on `globalThis.meruMeasure` naming each web contents, every tab's view a stage keeps among them (`Stage.kept()`), a detached one named so, both over `Stages.all`, which the suite and `pnpm measure` call through Playwright's `app.evaluate` with `scripts/lib/app.ts`'s `readExposed`. The suite reads the stage, profiles, entitlement and update state through the page's own snapshot channels.

## Profiles and state

`main/features/profiles/` owns `<userData>/profiles.json`, `{ version, data: { profiles, tabs, groups, selectedProfileId } }`, the records of `core/records/` held in memory and written through the `SnapshotStore`. The order of `tabs` is the sidebar's; `core/engines/ordering.ts` turns it into rows, a group of several tabs being one row whose tabs follow its layout's panes (`panes(group.layout)`), so a drop or a swap reorders them. Every change is a pure function of `core/engines/state.ts` and is committed only if `state-validate.ts`'s `validateState` finds nothing: ids are unique, panes included; the selected profile exists; every tab belongs to a profile and sits in exactly one group of that profile; a group is never empty and its layout's leaves show exactly its tabs, so a group of one is a single leaf; every profile has a tab; and a profile holds at most one tab of a single-instance app, which is why `validateState` takes the catalog's `isSingleInstanceId`. A tab of a single-instance app, Gmail, is pinned, which `core/engines/pinned.ts`'s `isPinned(tab, singleInstance)` derives from the catalog each time and nothing stores: `orderedTabs` puts a pinned tab's row first and the pinned tab first in its group, `canClose`, `moveTabTo`, `leaveGroup` and `joinTab` refuse it with `pinned` while another tab may still split beside it and leave its group, and `moveTab` puts a moved row below the pinned ones. `openTab` opens to a profile's one tab of a single-instance app rather than adding another; every engine function that asks takes `shared/apps.ts`'s `isSingleInstanceId`, the id form of `core/records/app.ts`'s `isSingleInstance(app)`. A tab joins a group at a `Placement`, a pane of the group and a `Beside`, `{ orientation, side }`, both declared with their schemas (`placementSchema`, `besideSchema`) in `core/records/layout.ts`, `before` putting it first and `after` second: `layout.ts`'s `split` makes the new pane there and `movePane(layout, paneId, targetPaneId, beside)` moves an existing one, keeping its id and reusing the id of the split it left, so `splitInto` moves a tab within its own group; `swap(layout, a, b)` and `equalise(layout)`, which evens each run of splits of one orientation, reach a group through the engine's `swapPanes(state, groupId, a, b)` and `equaliseGroup(state, groupId)`, which have no method or command yet. A file that half holds is mended by `state-repair.ts`'s `repairState`; one that cannot be read starts over as a first launch: one profile, "Personal", with a palette colour, one Gmail tab in a group of one, selected.

Main reads the state through the feature's methods (`selected()`, `currentGroup(profileId?)`, `group(id)`, `tab(id)`, `snapshot()`) and changes it only through its others (`createProfile`, `removeProfile`, `updateProfile`, which renames a profile or changes its colour, `selectProfile`, `openTab`, `closeTab`, `letSleep`, `moveTab`, `splitInto`, `leaveGroup`, `joinTab`, `focusTab`, `resize`, `swapPanes`, `equaliseGroup`), each returning a `Result`. `joinTab(tabId, targetTabId, beside)` puts a tab beside another's pane where `beside` says, out of its own group first when that is another, and `tabs.join` carries the orientation and side, the sidebar sending vertical-after; `focusTab` selects the tab's profile when it is another's and emits `tab.focused`, on which the main window shows the tab's group and the stage focuses its pane. A feature that follows the selected profile listens for `profile.selected`, which carries the group to show and comes before the `stage.invalidated` every change emits. A page seeds with `profiles.snapshot` and follows `profiles.changed`; `profiles.create`, `remove`, `select`, `update` and `tabs.close`, `move`, `focus`, `join`, `leave` are its requests. A profile's `status` carries the Gmail unread count its page last reported. Each tab in the snapshot carries `closeable`, what `canClose` answers for it, and `asleep`, which the sleep feature sets through `setAsleep` and nothing stores. A tab's stored `url` is the address its view starts at, never where its page has since gone. The feature declares `profiles.select1` to `select9` (Cmd/Ctrl+1 to 9) and `profiles.next` and `profiles.previous` (Cmd/Ctrl+Shift+] and [) in a Profiles menu, each stepping over deactivated profiles, and the global setting `profiles.unreadBadge` (default on), which shows the count on a profile's button. `createProfile` asks `canUse(entitlement, "extraProfile")` and returns the gate's refusal, such as `free`, as its error. A profile past the count the entitlement allows is deactivated, never deleted: the snapshot marks it `deactivated`, computed from the entitlement each time and never stored, it cannot be selected, and the selection moves off it when the entitlement changes, so it comes back whole with a trial or a license. Removing a profile drops its override layer from the settings and clears its session partition, `persist:<id>`, through `SessionPort`.

`main/features/windows/` owns `<userData>/windows.json`, `{ version, data: { windows } }`. The main window opens at its saved bounds, moved and shrunk by `core/engines/bounds.ts`'s `clampToDisplay` into a display that is still there, or at the default size centred on the primary display; its bounds are written a second after it moves or resizes and at once when it closes. It shows its saved group while that is a group of the selected profile, and the profile's current group otherwise, as the pure `core/engines/windows.ts`'s `mainGroupOf(windows, state)` decides; the saved group changes on `profile.selected` and `tab.focused`.

## Chrome page

The chrome page (`renderer/pages/chrome.html`) draws the titlebar, the sidebar and the dividers; the window is `titleBarStyle: hiddenInset` on macOS and `hidden` with a `titleBarOverlay` on Windows, and on Linux while the global `window.linuxControls` is on, as `core/engines/chrome.ts`'s `titleBarOf` decides, its overlay a pixel short of `TITLEBAR_HEIGHT` so classic's seam runs under the window controls. `Theme` and `themeSchema` are `core/records/theme.ts`'s, and `themeOf(port)` beside the `ThemePort` reads it. A page takes its platform from its URL's `platform` and its first theme from `theme`, then follows the `theme.changed` push; `main/features/appearance/`'s `Appearance` follows the theme, having each window's `recolour(theme)`, the main window's and the settings window's, paint it and its title bar overlay and broadcasting `theme.changed` to every page (`renderer/theme.ts`), and every page entry follows it and renders through `renderer/page.tsx`'s `mountPage(client, node)`, the overlay page over the client it builds from `overlays[kind]` once; Chromium's `prefers-color-scheme` is not read, since it misses `nativeTheme.themeSource`. Main loads a page through `main/shell/window.ts`'s `pageUrl(pages, file, query)`, from `dist/renderer` or, under `pnpm dev`, from the dev server whose base `MERU_RENDERER_URL` names, adding the platform and theme. `renderer/client-context.tsx`'s `defineClientContext<Surface>(page)` gives a page's client a provider and a hook, `ChromeProvider` and `useClient` for the chrome page. Each synced copy has its store and context beside its hook, `useProfiles` (`features/profiles/use-profiles.ts`), `useStage`, `useSidebar` and `useSetting`, built over `renderer/store.ts`'s `syncedStore` from any client whose surface holds its snapshot and push. The chrome's ground and ink come from one table, `core/engines/chrome.ts`'s `chromeColors`, a neutral grey (`#ececf1` with `#2a2a30` light, `#1d1d24` with `#e2e2ea` dark) that `renderer/theme.ts` sets as `--chrome` and `--chrome-foreground`, the chrome page's ground and ink and the settings window's `--sidebar`, and the window takes as its background and title bar overlay; the panes keep Google's own white or near-black on it. `renderer/ui/` holds shadcn's base-nova components over base-ui, generated with `pnpm exec shadcn add <name> -p renderer/ui` from `app/`, and `globals.css` the theme tokens. Anything the chrome page draws past the titlebar and the sidebar would be under the panes, so a control's tooltip is a native `title`, `useTooltip(label, commandId?)` appending the command's shortcut in the platform's glyphs, and a popover is a stage overlay. Every string a user sees goes through `msg`.

`renderer/features/titlebar/` is the bar across the top, a drag region but for its controls, laid inside `env(titlebar-area-*)`: back, forward and reload, which run `stage.back`, `stage.forward` and `stage.reload` and are titled with their shortcuts, reload being `stage.stop` while the pane loads; a button per profile the entitlement allows, none while there is one, the selected one `secondary`, with its colour, a mark when it needs signing in and its unread count, the row scrolling with arrows when it overflows; and, while the sidebar is hidden, the launcher button.

## Sidebar

The sidebar down the left of the chrome page shows the selected profile's tabs while it has more than one; the pure `core/engines/sidebar.ts`'s `sidebarOf` decides it, `narrow` (64px, icons) or `wide` (224px, titles too) from the profile setting `sidebar.width` (`auto`, `narrow`, `wide`), `auto` being wide once an app has several unpinned tabs. `main/features/sidebar/` holds what the user hid or flipped per profile for as long as the app runs, answers `sidebar.snapshot`, and on a change pushes `sidebar.changed` to the pages and emits the `sidebar.changed` event, on which the stages lay out again. It declares `sidebar.toggle` (Cmd/Ctrl+S) and `sidebar.toggleWidth`, both in the View menu, the first enabled only while the profile's tabs call for a sidebar (`hasSidebar`) and the second only while it shows; the menu is rebuilt whenever the sidebar changes. `renderer/features/sidebar/` draws a row per tab in `tabs` order, the focused pane's tab active, a group's rows inside a dashed outline, the Gmail row's unread count under `sidebar.gmailUnreadBadge` (`always`, `whenInactive`, `never`), and at its foot the launcher button and, under `sidebar.showWidthToggle`, the width toggle; its width eases over 200ms unless motion is reduced. The launcher button is `renderer/features/launcher/launcher-button.tsx`, so the chrome page's chunk carries none of the launcher's own code, and the width toggle is `width-toggle.tsx`. The rows are a `tablist`: each row's button is a `tab`, the active one holds the one tab stop, the arrow keys, Home and End move focus through them, and Enter or Space brings one to the front. A sleeping tab's row is drawn at half opacity, as 3.x draws one. A row reveals 3.x's close control on hover and closes on a middle click, both through `tabs.close`, except on a tab the profiles snapshot marks not `closeable`. A pinned tab's row, `isPinned`, is drawn as 3.x draws a pinned tab, its icon alone, `outline` while inactive and across the strip when wide, with no close control, and is no dnd-kit drag source. Every other row is a dnd-kit draggable, and every row a droppable; the target under the pointer and the pointer's height on it give the zone (`zoneAt`), and on release `dropAction` decides, through `use-tab-drop.ts`'s `useTabDrop`: between rows it moves (`tabs.move`), or leaves its group for a row of its own (`tabs.leave`); onto another group's row it joins that group (`tabs.join`). Once the pointer leaves the sidebar the drag is the stage's: the page sends `stage.beginDrag` with `{ kind: "tab", tabId }` once, `stage.dragTo` with every move and `stage.endDrag` on release, which it keeps getting the pointer for while the button is held, and sends `stage.cancelDrag`, which ends the stage's drag with nothing dropped, if the pointer comes back or dnd-kit cancels; `renderer/features/stage/tab-drag.tsx`'s `TabDrag` draws the row beside the pointer and the tint, `dropRect` of the zone under it, in `accent` at 15% with a 2px outline at the pane's radius. The launcher is a view of its own over the panes rather than a dropdown in the chrome page, because the panes are native views stacked above the chrome page and would cover anything it drew past its strips.

## Launcher

`main/features/launcher/` opens the launcher as a stage overlay over the window's panes on `launcher.open`, which the launcher button sends, and on the command `launcher.open` (Cmd/Ctrl+T, File menu), and closes it on `launcher.close`. The page is `renderer/pages/overlay.html?kind=launcher`: `overlay.tsx` shows an overlay by the kind its address names, each with its own client on the surface `shared/channels/surfaces.ts`'s `overlays` gives that kind, the launcher's being `launcherSurface`, and only the stores it reads; `Stage.openOverlay(kind, url)` names the same kind's surface to the preload, and a new overlay is a kind in `overlayKindSchema` and an entry in that table. The launcher is shadcn's command dialog, `command` (cmdk, its own filtering off) in `dialog`, centred over the window above a transparent backdrop of the page's own, which catches a click outside since the overlay view covers the window; it lists the apps of the global setting `launcher.apps` (the catalog's ids, in its order by default) less the single-instance apps, Gmail, whose one tab a profile always has open, narrowed as one types by `core/engines/launcher.ts`'s `launcherApps`; Enter or a click sends one `stage.openTab` for the selected profile, Shift asking for a vertical split and a launcher opened for a split asking for its orientation, and closes it. Escape, a click on the backdrop and the window losing focus close it. `dialog` is in `renderer/ui/` for the overlay page alone, so it and base-ui's dialog stay out of the chrome page's chunk.

## Sleep

A tab sleeps only when the user lets it: its record's `sleeps`, off by default, which `Profiles.letSleep` sets and refuses with `pinned` on a pinned tab, and the command `sleep.toggleTab` (View menu) flips for the window's focused tab. `core/engines/sleep.ts`'s pure `sweep` decides from the tabs, when each was last seen, which a pane shows (`Stages.shown()`), which play sound (`Stages.audible()`) and the clock: a tab the user let sleep (`maySleep`, never Gmail's pinned tab, whose loaded page keeps the session's cookies fresh) falls asleep once it has been out of sight and silent for the global `sleep.afterMinutes` (default 60, on the Sleep settings page); a shown tab is awake; every other keeps its state. It answers when the next tab is due, or null. `main/features/sleep/`'s `Sleep` runs it on `stage.invalidated`, `tab.focused`, a change of the setting and at that due time only, so no timer runs while no tab can sleep; it lets go of each tab falling asleep's views through `Stages.sleep` and hands the asleep set to `Profiles.setAsleep`, held in memory and carried as each snapshot tab's `asleep`, never stored. The sidebar draws a sleeping row at half opacity, and showing the tab wakes it: the stage makes it a new view at its stored address. `MERU_SLEEP_MINUTE` sets how many milliseconds a minute of the setting lasts in a run from the repository, which `tests/sleep.e2e.ts` shortens to watch a tab fall asleep and wake.

## Inbox

`main/features/inbox/` reads the Gmail Atom feed of each profile that is not deactivated, `https://mail.google.com/mail/u/0/feed/atom` with a `?t=` cache-buster, through `SessionPort.fetchText` in the profile's partition, so the request carries its cookies; `fetchText` follows no redirect, answering one as `redirected` with its `Location`, reads at most `SESSION_BODY_CAP` (1 MB) of a body, answering `tooLarge` past it, and gives up after its timeout; `core/engines/feed.ts`'s `parseFeed` turns the text into the unread count Gmail states (`fullcount`, which can exceed the twenty entries listed) and the entries. It reads every feed on `start()`, then each one 30s after its last read, doubling the wait after each failure up to five minutes (`core/engines/inbox.ts`'s `feedDelay`), reads nothing while offline, and reads every feed at once when the network returns or the machine wakes. A read answered with a redirect, which over HTTPS only Google can send and only to sign-in, or a 401, sets the profile's status to `needsSignIn` without asking the sign-in page; a good read sets `{ kind: "ok", unreadCount }` through `Profiles.setStatus`, which tells pages only when the status changed and touches no stage, and the titlebar and the sidebar show it. A run of failures writes one warning when it starts and one when its cause changes (network, signed out, too large, an HTTP status, a parse error), not one per read, and an info line once the feed reads again. `readFeed(memory, entries, readAt)` decides which entries arrived since the last read: the first read only remembers; after it, an entry is new when the last read did not list it, no read has, and it was issued no earlier than five minutes (`FEED_SLACK`) before the last read, so mail marked unread again is not new; it remembers an entry only while that slack could still call it new. New mail goes out as the `mail.arrived` event, oldest first, and any change to what a feed lists as the `inbox.changed` event, whose readers ask `Inbox.feeds()`; no page reads the inbox, so it has no channels. The inbox follows the `profiles.changed` event, which the profiles feature emits when the profiles themselves change, never on a tab or group change. `main/features/badge/`'s `Badge` shows the unread badge, the dock's on macOS, the launcher count on Linux and the taskbar overlay on Windows, which `core/engines/badge.ts`'s `overlayPixels` draws since the main process has no canvas: the total of every profile whose `inbox.countUnread` (profile scope) is on, while the global `inbox.unreadBadge` is, through `BadgePort`. `MERU_GMAIL_URL` points a run from the repository at a stand-in mailbox, such as `tests/feed-stub.ts`'s on loopback, whose feeds, message pages and sign-in redirect hang off it as they do off `https://mail.google.com/mail/u/0`; under `MERU_E2E` or `MERU_MEASURE` without it no feed is read, so no test run asks Google.

`main/features/notifications/` shows, on `mail.arrived`, one notification per new email through `NotificationPort` while the profile's `notifications.enabled` is on: the sender as the title (`[profile] sender` once there are several profiles) or the profile under `notifications.showSender` off, the subject as macOS's subtitle and the snippet as its body, or both in the body elsewhere, under `showSubject` and `showSummary`, silent unless `playSound`; `notifications.newEmails` (Pro, profile scope) set to `important` keeps only the email the Important feed (`^iim`) lists, read only then, and all of it when that feed fails. More new emails at once than `MAX_MAIL_NOTICES` (five) raise one notification, "N new emails", that opens the inbox instead, as `core/engines/notifications.ts`'s `mailNotice` decides, beside `notifiable` and `messageUrl`. A click reveals the main window, loads the message into the profile's Gmail tab through `Stages.load`, which starts the tab's next view there while no stage keeps one, and focuses it. The platform port holds each shown notification until it is clicked, closed or fails, because Electron drops a notification's listeners once nothing references it. Archive and mark-as-read actions are not offered: Gmail answers its action endpoint with 200 and a script sending the page to sign-in when it refuses, so main cannot tell a refusal from success without a signed-in session to try it on.

`main/features/tray/` puts the icon in macOS's menu bar or the system tray elsewhere under `tray.icon`, off by default on macOS and on elsewhere through the setting's `platformDefaults`, with the unread total beside it in the menu bar under `tray.unreadCount`, in `tray.iconColor`'s shade or the one that reads on the theme, with an unread variant, Windows taking 3.x's multi-size ICO files. Its menu lists each profile with its count, which selects it and shows the window, then Show or Hide Meru and the platform's quit; a click hides the window or shows it, first selecting the first profile with unread mail under `tray.selectUnread`, except on Linux, whose tray sends no click. It renders from one function when the profiles, the inbox or its settings change, never on a stage change, through `TrayPort`. Under `MERU_E2E` the badge, the notifications and the tray are `main/shell/e2e.ts`'s `recordingDesktop()`, which the inspector answers as `badge`, `notifications` and `tray`, and whose `click(index)` the suite reaches through the function main leaves on `globalThis[E2E_CLICK_NOTIFICATION]`. The settings sit on the Inbox page.

## Logging

Every feature and shell object takes a `log: LogPort` (`core/log.ts`) through its constructor, which `main/index.ts` scopes to it: `debug`, `info`, `warn` and `error`, each a message that stays the same from one occurrence to the next and a fields object for what varies, which `core/log.ts`'s `logLine` writes under `fields`, so no field can pass for the envelope and the type refuses its names, an `error` field written as `{ name, message, stack }` by `core/errors.ts`'s `serializeError`. Every text of a line is redacted at any depth, URL query strings, bearer and cookie values and email addresses, each text cut at 4 KB and a line past 16 KB written as its envelope and the length it would have had. `main/platform/log.ts`'s `createFileLog` writes one JSON line per entry to `<userData>/logs/main.log` through one queue, moving it to `main.old.log` once the next line would pass 5 MB; an installed app keeps `info` and above, a run from the repository keeps `debug` too and mirrors every line to the console; the quit waits on its `flush`, which settles only once the lines written while it waited are on disk too. `main/shell/failures.ts`'s `logFailures` writes what `LifecyclePort.onFailure` reports: an uncaught exception, an unhandled rejection, a process that ended other than cleanly and a console error of the app's own pages, never Google's. A handler that throws across IPC answers `threw` with the error serialized beside the message. A test that expects nothing to go wrong passes `test/fakes/log.ts`'s `strictLog`, which fails the test on a warning or an error through `expect.soft`, without throwing into the code that wrote it; one that reads what was written passes a `FakeLog`'s `scoped(scope)` and reads `at(level)`.

## Links

`core/engines/links.ts`'s `resolveLinkTarget` decides where a link followed in a pane goes, from the catalog in `shared/apps.ts`, the tabs and groups, and the settings. `ViewPort.onOpen` hears each link a page opens, with its `Disposition` (`core/records/link.ts`): from Electron's window-open handler, `window` for a new window, `background` for a background tab, else `default`, and from `will-navigate`, `inPlace`; and a listener answering true takes it from the page; `TabViews` subscribes for each tab, and the stages hand each link, through the `onOpen` and `onPopup` options `main/index.ts` gives them, to the links feature, `main/features/links/`'s `Links`, which declares its settings in its own `settings.ts` and carries out what `resolveLinkTarget` decides under the global settings `links.openInApp` (default on) and `links.excludedApps` (none), 3.x's defaults, both `tier: "pro"`. A page navigating itself and a window onto `accounts.google.com` are left to Chromium, so sign-in and its redirects stay in the pane; `samePane` loads the link in the pane (`Stages.load`, every stage keeping a view of the tab); `newTab` loads it in the profile's tab of that app when it has one, or, through `Stages.load`, which starts the tab's next view there while no stage keeps one, and focuses it, and otherwise opens a tab at the link through `Profiles.openTab(profileId, appId, placement?, url?)`, split beside the pane and focused for a foreground link, in a group of its own and unfocused for a background one, as 3.x opens a background tab; `window`, which a click asking for a new window or an app that opens as one gives, opens a plain tab in a group of its own and focuses it, never a split, until the windows feature can open a group window; `external` goes to the default browser through `ShellPort.openExternal(url)`, whose rejection, when nothing on the system opens the address, the links feature writes as a warning, and which under `MERU_E2E` is `main/shell/e2e.ts`'s `RecordingShell`, whose addresses the inspector answers as `external`. A blank popup, `window.open("about:blank")`, as Google's OAuth opens, is made hidden by the platform view and reported through `ViewPort.onPopup(listener(url))` at its first navigation: `core/engines/links.ts`'s `isSignIn(url)` decides, showing it only when that is `accounts.google.com`, and otherwise `Links.popup(url)`, which the stages' `onPopup` calls, sends the address to the browser and the popup is destroyed, as 3.x's `handleWindowOpen` does. A blank popup that never navigates, such as one a page writes into for printing, is destroyed after `BLANK_POPUP_TIMEOUT` (5s) in `main/platform/views.ts`; `tests/popup.e2e.ts` holds the three cases against Electron, behind a proxy on a closed port so nothing leaves the machine.

## Settings

A feature declares its settings in its own `settings.ts` with `defineSetting("feature.name", { schema, default, scope, tier, restart, page, label, description?, options?, platforms?, platformDefaults? })`, `platformDefaults` replacing `default` on the platforms it names, which main and the settings page read through `core/engines/settings.ts`'s `forPlatform(specs, platform)`, and adds the list to `shared/settings/registry.ts`, the one place they are assembled; the key's form, the default against the schema and every reader's value type are checked by `tsc --build`. Most settings are `scope: "global"`. A setting is `scope: "profile"` only when its value is about that profile's page or mail, such as `stage.zoom`; only those may be overridden per profile, which the `Settings` type refuses at compile time and `core/engines/settings-parse.ts`'s `parseSettings` drops at load. A value resolves as the profile's override, then the global value, then the default (`core/engines/settings.ts`).

`main/features/settings/` keeps them in `<userData>/settings.json`, `{ version, data: { global, profiles: { <id>: overrides } } }`, through the `SnapshotStore` in `core/snapshot.ts`, which parses per key so a bad value costs only itself, writes debounced and on quit, and keeps a corrupt file beside it as `settings.json.corrupt`. Main alone resolves the gate: a setting declared `tier: "pro"` is locked while `canUse(entitlement, "proSetting", { now })` refuses, resolving to its default in `settings.get` whatever is stored, and `settings.set` refuses a write to it; `settings.snapshot` and `settings.changed` carry the locked keys with their `GateRefusal` beside the layers, and when the entitlement changes every subscriber, profile-scoped ones too, hears each Pro key, the stored value being kept for when the gate allows it. `canUse`'s context is `{ now }`, and `{ now, profiles }` only for `extraProfile`. `settings.set`'s payload is `SettingSet` (`shared/settings/schema.ts`), a union of `{ key, value, profileId? }` per key typed from the registry, `profileId` only on a profile key, which `settingSet(key, value, profileId?)` builds and the dispatcher parses. Main reads with `settings.get(key, profileId?)` and reacts through `settings.subscribe`; a page reads with `useSetting(key, profileId?)` from `renderer/features/settings/use-setting.ts`, the default while the key is locked, and `useLocked(key)` for the refusal, seeded by `settings.snapshot` and kept by the `settings.changed` push. A run from the repository (`pnpm dev`, the end-to-end suite) also follows hand edits to the file; an installed app does not watch it.

## Settings pages

`settings.open` (Cmd/Ctrl+,, in the app menu) opens the one settings window, `main/features/settings/window.ts`'s `SettingsWindow`, which registers the command's handler itself, 1000 by 720 on the primary display with the chrome's title bar and ground (`windowColours`), or brings it to the front. Its page, `renderer/pages/settings.html`, is on `settingsSurface`, which holds the settings, profiles, commands, updater and shortcuts domains. `renderer/features/settings/settings-window.tsx` lays it out as 3.x does, under a titlebar on the chrome grey with a seam below it, the pages down the left, a seam, and the page on the right, on `--background` for every page, one surface on shadcn's sidebar tokens (`--sidebar`, `--sidebar-foreground`, `--sidebar-accent` and their kin in `globals.css`, over the chrome's greys), each section of a page a card (`settings-section.tsx`'s `SettingsSection`, over `renderer/ui/card.tsx`) whose rows a line divides, its heading above it in sentence case: a setting's `section`, the page's settings with none sharing the card under its title, and the bespoke pages' lists alike, the page named by the address's hash through `renderer/use-hash.ts`'s `useHash`. A feature declares its pages once in its `settings.ts` with `defineSettingsPage(id, { label, icon, order })`, `icon` the name of the lucide icon before its label, which `renderer/features/settings/page-icons.ts` maps to its component and `tsc --build` holds to every name a page gives, and `shared/settings/registry.ts` assembles them, sorted, as `settingsPages`, whose ids type `defineSetting`'s `page`; a page with content of its own beyond the registry's fields registers it in `renderer/features/settings/contents.ts` as a `PageContent`. A page's fields come from the registry by `page`, a list after the one-line fields, a setting with `platforms` (`core/records/platform.ts`'s `Platform`) only on those. `field-kind.ts`'s `fieldKindOf` reads a schema's kind and `controls.tsx` holds one field component per kind: a boolean as a switch, a string union as shadcn's `select` naming each value by the setting's `options`, which the type requires of an enum, a number as an input within the schema's bounds, a string as an input, and an array of an enum (`multiChoice`), such as the app ids of `appIdSchema`, as 3.x's checkboxes, the picked ones sortable with dnd-kit. The schema is the validation, and typing writes through `use-draft.ts`'s `useDraft` once it pauses, over `renderer/use-debounced.ts`'s `useDebounced`, which flushes when the input loses focus or the component goes, the input then showing the value in force again. `setting-field.tsx`'s `SettingField` shows a setting's label and description, a `tier: "pro"` setting locked at its default with the gate's reason while main says it is locked, a `restart` setting saying so, and under a `scope: "profile"` setting a switch that gives the selected profile its own value, taken from the value in force, and turned off removes it. Every write is `settings.set` and comes back as `settings.changed`.

A value no field component edits has a page of its own. The shortcuts page, `renderer/features/shortcuts/shortcuts-page.tsx`, lists every command by the registry's `commandSections`, in their order, each with a recorder that writes the next key pressed on it into `shortcuts.bindings` through `core/engines/shortcuts.ts`'s `acceleratorOf`, the platform's command key as `CommandOrControl`, Backspace or Delete taking the shortcut away and Escape stopping, sending `shortcuts.recording` while it records so that the settings window ignores the menu's accelerators (`WindowPort.setIgnoreMenuShortcuts`) and the key reaches it, a reset to the default, and the commands `conflicts` finds marked. The profiles page, `renderer/features/profiles/profiles-page.tsx`, lists every profile in order, a deactivated one marked and kept, each edited in place: the label written through `profiles.update` by `useDraft`, validated by `profileSchema`'s label trimmed, taking emoji from the system's own picker, the colour from the palette at once, and removing it behind a question; a dialog adds one while `extraProfile` is allowed, and the gate's refusal stands where its button would. The updates page shows the update state with Check for updates, or Restart to update once one is ready (`renderer/features/updater/`). The page's tests mount it with `renderer/testing.tsx`'s `mountSettings`.

## Commands

Every action a user can trigger is a command, declared by its feature in `commands.ts` with `defineCommands("feature", { name: { label, shortcut?: { default, darwin? }, menu?: { section, order } } }, { label, order })`, `darwin` replacing `default` on macOS, which makes the id `feature.name`, the last argument naming the feature's section on the shortcuts page, and handled through the `CommandRegistrar` its constructor takes. `shared/commands/registry.ts` assembles every feature's commands, with `commandSections` and the typed `commandById`; the pure `core/engines/menu.ts`'s `buildMenu` lays the menu out from them, over the records of `core/records/menu.ts`, `main/shell/menu.ts`'s `ApplicationMenu` hands it to Electron, and a page runs one with `client.invoke(commands.run, { id })`. A command's shortcut is its default unless `shortcuts.bindings` maps its id to another accelerator, or to `null` for none; `core/engines/shortcuts.ts` parses, normalises and resolves them for the platform (`resolveBindings(commands, bindings, platform)`) and reports conflicts. The menu carries the resolved shortcuts, which is what makes one work while a pane has focus, and is rebuilt when the bindings change or on `menu.invalidated`; the first menu is named for the app on every platform, as 3.x has it, holding About, the `app` section's commands, macOS's own roles only there, and Quit; a File menu holds the `file` section's commands and a History menu the `history` section's. A handler sees the command's context, `{ windowId }`, the window it was given for, or null while the menu asks with no window open, and a handler given as `{ run, when }` runs only while `when(context)` holds, the menu showing it disabled otherwise. A command with a shortcut and no menu item is run by `main/shell/keys.ts`'s `ShortcutKeys`, attached to the chrome page and every pane with their window's id, from `before-input-event` while some such command has a key, through `matchShortcut`, which matches the physical key and exactly its modifiers; a key whose command's `when` is false is not prevented and reaches the page.

## IPC

A domain's channels are declared once in `shared/channels/<domain>.ts` with `defineChannels` and zod schemas, and a surface in `shared/channels/surfaces.ts` lists the domains a kind of page may use. Callers pass the channel objects, never names: the renderer's `client.send(stage.split, payload)`, a feature's `registrar.register(stage, { split: handler, … })`, `registrar.push(contentsId, stagePushes.changed, snapshot)` to one page and `registrar.broadcast(settingsPushes.changed, payload)` to every page whose surface has the push. A page settles main's answer through `settle` in `shared/channels/define.ts`, and seeds and follows a snapshot through `renderer/store.ts`'s `syncedStore`. A renamed channel, a changed schema, a missing handler or a channel of another surface fails `tsc --build`; at runtime the preload's allowlist and the dispatcher in `main/shell/ipc.ts` refuse anything outside the sender's surface and parse every payload before a handler sees it. Main names a page's surface to the renderer's preload in its command line, `--meru-surface=<name>` for one of `pageSurfaces` (`chrome`, `settings`, `launcher`, `tabDrag`), and the preload allows that surface's channels; a page named nothing is allowed nothing.

## Measure

`pnpm measure [--profile <name>] [--samples <n>] [--idle <seconds>] [--blank] [--floor[=view]]` launches the built app and reads every process, by kind (main, chrome page, pane, overlay, gpu, utility), at five points: 5s after launch, right after one split, while the split's tab is dragged across the panes, with the launcher open, and after a minute idle once it has closed. It prints each kind's largest memory and mean CPU per point, and appends one JSON line, with the host, to `measurements/darwin.jsonl`, which is committed and keeps its newest 500 lines. The file records the maintainer's Mac mini only, so its lines stay comparable: a run appends only when its hostname matches the first line's or `MERU_MEASURE_HOST`, and otherwise says it did not record. `--floor` also measures `scripts/floor/`, a bare Electron app with one sandboxed window, and `--floor=view` the same with one view, and prints them beside Meru. Memory is private for main and the working set for the rest, which is all Electron reports on macOS. `pnpm test:budget` fails if any process uses more than 2% CPU at idle or main or the chrome page grows more than 10MB from launch to idle.

Both run by hand on macOS, not in CI, before pushing a change that could move the numbers; the run's line is committed with the change and its commit message says what moved.

## Entitlement

The entitlement is derived from a token the API signs, JWT-shaped with `alg: EdDSA` and a `kid`, and verified on the device. `core/entitlement/token.ts` parses it and declares the claims; `verify.ts` checks the key, the Ed25519 signature through `crypto.subtle`, the device id and the expiry with a skew allowance; `derive.ts` turns claims into the `Entitlement` record (`core/records/entitlement.ts`: `unknown`, `free`, `trial`, `licensed`, `disabled`, with `source` and `expiresAt`); `gate.ts`'s `canUse` is what a Pro action asks, with `unknown` gating as free. `main/features/entitlement/` keeps `entitlement.json`, `{ version, data: { deviceId, licenseKey, token: { value, licenseKey }, lastAnswer, rejected } }`: `open()` verifies the stored token with no network, `attach()` answers the `entitlement.snapshot` channel before the window shows, and `start()`, after it, asks the `EntitlementApi` port for a token whenever there is none, it has expired or it was issued for another license key, at once when online, on the network's return when not, at the token's expiry through the clock, after a failure at a growing interval, and when the machine wakes; what is due and when are the pure `core/entitlement/schedule.ts`'s, of the stored state, the claims and the time. A rejected license key is asked about again an hour later; meanwhile the device asks for its trial while the trial has not ended, and is free once it has or when it holds no trial token. It never shows anything; a change reaches every page as the `entitlement.changed` push and features as the `entitlement.changed` event.

The app POSTs `{ licenseKey, deviceId }` to `MERU_ENTITLEMENT_URL`, or the placeholder in `core/entitlement/api.ts`, and takes `{ token }` from a 200 and `{ error: { reason } }` from a 4xx. To run against a local stand-in, `node tests/entitlement-stub.ts` serves the end-to-end suite's stub, which signs with the development key, answering a trial with no license key and Pro for `PRO-KEY`, and prints the `MERU_ENTITLEMENT_URL=…` to launch `pnpm dev` with. To put a token in place by hand, `node scripts/entitlement/sign.ts claims.json` prints one for claims such as `{ "sub": "<deviceId from entitlement.json>", "plan": "pro", "deviceLimit": 3, "ttl": 10800, "status": "active" }`.

`core/entitlement/keys.ts` holds the Ed25519 public keys a token may be signed with, by `kid`, compiled into the bundle. The development key, `dev-2026-11`, is not a secret: its private half is `scripts/entitlement/dev-private.pem`, and only a run from the repository accepts it, never an installed app. A production key is added to `productionKeys` by a release, before the API signs with it; the app never fetches a key.

## Packaging

`packaging/` is a workspace package of its own whose one dependency is electron-builder, so the app's dependencies stay what the app loads. `packaging/electron-builder.config.ts` is the config, typed through `Configuration`; it packs `app/` and takes the description and the Electron version from `app/package.json`; and `packaging/assets/` holds the icons, `Assets.car`, which carries the icon `CFBundleIconName` names, and the NSIS include. The asar holds `app/dist/` without source maps and without `node_modules`, since main and the preloads are bundles. `pnpm package` builds and packs an unpacked app for this machine (`packaging/out/mac-arm64/Meru.app` here); `pnpm package:mac`, `package:linux` and `package:win` pack that platform's installers with `--publish never`, and pass anything after them to electron-builder, such as `pnpm package:linux AppImage --x64`. All four run `scripts/package.ts`. `packaging/out/` is ignored.

The fuses are 3.x's: `runAsNode`, `enableNodeOptionsEnvironmentVariable` and `enableNodeCliInspectArguments` off, asar integrity and `onlyLoadAppFromAsar` on, `grantFileProtocolExtraPrivileges` on because the renderer is a `file://` page, `enableCookieEncryption` off because it is one-way. The app id is 3.x's, `sh.zoid.meru`, so an installed app shares 3.x's user data directory. A `pnpm package*` build is marked local instead: `scripts/package.ts` sets `MERU_LOCAL_PACKAGE=1`, the config then adds a `local-package` resource holding the checkout's absolute path, and main, finding it, keeps the app's user data in `<checkout>/.meru/packaged`. In GitHub Actions (`GITHUB_ACTIONS=true`) the script leaves the variable unset, so a CI build has no marker and uses Electron's default, as a release does.

### Signing

A build signs only from its environment, all of a platform's names or none of them. macOS: `CSC_LINK` and `CSC_KEY_PASSWORD` (the Developer ID certificate as a base64 `.p12` and its password) and `APPLE_API_KEY`, `APPLE_API_KEY_ID`, `APPLE_API_ISSUER` (the App Store Connect key for notarisation; `APPLE_API_KEY` may hold the key's contents, which `packaging/hooks.ts` writes to a temporary file because notarytool takes only a path). Windows: `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`, which Azure Artifact Signing's credential reads. `packaging/signing-env.ts`'s `hasSigningEnv("mac" | "win")` says whether a set is complete and throws on a partial one, since electron-builder would sign with what it finds and silently skip the rest; `scripts/package.ts` calls it before building for `--mac` and `--win`, and the config leaves `azureSignOptions` out without the Windows set. With no env a local package is unsigned (macOS: unsigned unless the keychain holds a Developer ID identity, and never notarised).

macOS signs with the hardened runtime and `packaging/assets/entitlements.mac.plist`, which holds exactly JIT, unsigned executable memory, DYLD environment variables, camera and microphone; there is no provisioning profile or keychain access group. Windows signs through `win.azureSignOptions` with `verifyUpdateCodeSignature: true`, so `publisherName`, `CN=Zoid Ltd, O=Zoid Ltd, L=London, C=GB`, goes into `app-update.yml` and an installed build refuses an update signed under any other subject; it has to stay the certificate's subject exactly.

The values live as GitHub repository secrets on `zoidsh/meru`, sourced from 1Password as `$PROJECT_DOCS_DIR/shared/electron-macos-signing.md` and `$PROJECT_DOCS_DIR/zoidsh/meru/windows-code-signing-setup.md` describe; only the build workflow reads them. How a signed build is produced and what is still missing is in `$PROJECT_DOCS_DIR/zoidsh/meru/next/release.md`.

## CI

`.github/workflows/ci.yml` runs on every push to `next`, every pull request and by hand. `check` runs `pnpm check` on Linux. `e2e` runs on `ubuntu-latest` and `windows-latest`, not macOS, whose runners GitHub rations and whose suite runs on the maintainer's Mac before every push: `pnpm build` and `pnpm test:e2e` against the unpacked `app/dist/` (under `xvfb-run` on Linux, with `-noreset` so the X server survives the moment between two launches), plus `pnpm test` on Windows, where paths and the shell differ; a failed run uploads `test-results/`. `package` packs a Linux x64 AppImage through `pnpm package:linux AppImage --x64`. Steps run in bash on every OS, and pnpm's store is cached per OS. The e2e suite launches `app/dist/` with Playwright directly, never a packaged app.

`.github/workflows/build.yml` runs only by hand (`gh workflow run build.yml --ref next`). On macOS, Linux and Windows it runs `pnpm package:<platform>` with that platform's signing secrets, so macOS is signed and notarised and Windows signed, and keeps the installers as the run's artifacts for 14 days: `meru-mac` (dmg and zip for x64 and arm64), `meru-win` (one NSIS installer and one portable exe, each holding x64 and arm64), `meru-linux` (AppImage, deb and rpm for both). It publishes nothing: there is no release, no tag trigger and no update feed.

## Updater

`main/features/updater/` holds an `UpdateState` (`core/records/update.ts`: `idle`, `checking`, `available`, `downloading` with a percent, `ready` with a version, `error`) over the `UpdaterPort`, which `main/platform/updater.ts` implements with electron-updater, downloading by itself and installing on quit. `attach()` answers `updater.snapshot` and registers the commands before the window shows; `start()`, after it, does nothing unless the app is packaged, and otherwise checks 10s later and then every `updater.intervalHours` (global, default 4), and at once when `updater.channel` (global, `stable` or `beta`, which asks for prereleases) changes. Each updater event moves the state through the pure `core/engines/update.ts`'s `advance`, and every change is pushed as `updater.changed`. `updater.check` ("Check for updates…") answers `notPackaged` in a run from the repository; `updater.install` ("Restart to update") is enabled only while an update is ready, through its handler's `when`, and the menu rebuilds on the `menu.invalidated` event. Both sit in the app menu, with no default shortcut.

The feed is the GitHub releases of `zoidsh/meru`, which electron-builder writes into `app-update.yml` in the app's resources when it packs an installer target; an unpacked `pnpm package` app has none, so its check ends in `error`. To try an update by hand, pack the same app twice with a higher `version` in `package.json` the second time, serve the second build's `packaging/out/` with `npx http-server packaging/out -p 8080`, and write `Contents/Resources/app-update.yml` (`resources/app-update.yml` on Linux and Windows) in the first build as `provider: generic` and `url: http://localhost:8080`; then launch it with `MERU_BACKGROUND=1`, and it checks 10s after the window shows. Squirrel.Mac refuses an unsigned app, so on macOS that route needs two signed builds, such as two runs of the build workflow.

## Worktrees and profiles

A run from the repository keeps its user data under the checkout's `.meru/` (ignored by git), never in Electron's default directory, which is the installed app's: `.meru/<branch>`, or `.meru/default` on a detached HEAD, so every worktree and the main checkout run at once. `pnpm dev --profile <name>` picks `.meru/<name>`. Main applies the same rule before `ready` for any other unpackaged launch, such as `electron app` or `pnpm measure`, unless `--user-data-dir` names a directory, as the end-to-end suite's temporary ones do. The derivation is `@meru/user-data` (`packages/user-data/`), with `readBranch`, which both `scripts/dev.ts` and `main/platform/user-data.ts` import. `--background`, or `MERU_BACKGROUND=1` (set for Claude Code sessions in `.claude/settings.json`), opens the window behind whatever is in front; the end-to-end suite also sets `MERU_TEST_BACKGROUND=1`, which keeps the app from ever activating on macOS.
